# Project Identity & Developer Style

## Project

Pencatatan Keuangan — a personal finance tracking app (Flutter, Android + iOS). Local-first: transactions, categories, and accounts stored on-device via Drift/SQLite. No backend/cloud sync in the initial scope.

## Developer preferences

- [2026-09-22] - Wants a fintech-modern visual style: smooth micro-animations, shimmer loading states, clean rounded UI — referenced `flutter_animate`, `fl_chart`, `flutter_slidable`, `shimmer`, `flex_color_scheme`, `google_fonts` explicitly as the desired stack.
- [2026-09-22] - Wants documentation structured like the `Zemetiash` Next.js project: a root `CLAUDE.md` pointing to `docs/blueprint/*` (architecture reference) and `docs/knowledge/{THIS,LEARN}.md` (living knowledge system) — this file and its siblings are the Flutter adaptation of that pattern.
- [2026-09-22] - Comfortable with Indonesian in chat; code, comments, and docs stay in English per this project's convention (matches Zemetiash).

## Insights

- [2026-09-22] - Currency is Rupiah (`id_ID` locale, no subunit in everyday use) — always format with `intl`'s `NumberFormat.currency(locale: 'id_ID', symbol: 'Rp ')` and store amounts as whole-Rupiah integers, never `double`.
- [2026-09-22] - `flex_color_scheme: ^9.0.0` requires the new standalone `material_ui`/`cupertino_ui` packages (SDK-decoupled Material), which conflicts with this Flutter SDK's own bundled `ThemeData` (`return_of_invalid_type` on `FlexThemeData.light()`/`.dark()`). Pinned to `flex_color_scheme: ^8.4.0` instead, which still returns `package:flutter/material.dart`'s `ThemeData`. Re-evaluate the 9.x upgrade once the installed Flutter SDK has fully adopted the decoupled Material/Cupertino packages.
- [2026-09-22] - Grouped settings/menu screens (e.g. `features/profile`) follow a reusable pattern: a `ProfileMenuSection(title, items: List<ProfileMenuItem>)` widget rendering one rounded `surfaceContainerHigh` card per section with divided `InkWell` rows — avoids repeating `ListTile` boilerplate per screen. Destinations that don't have a route/screen yet show a "segera hadir" `SnackBar` via a local `_comingSoon` helper instead of fabricating a `go_router` route, keeping `flutter analyze` clean until the real screen exists.
- [2026-09-22] - `FloatingNavBar` ([floating_nav_bar.dart](../../lib/core/widgets/floating_nav_bar/floating_nav_bar.dart)) wants a pronounced "floats above the screen" look, not a typical flush bottom nav: a fixed `AppSpacing.xl` gap from the bottom edge (never touching it), a large `28`px pill radius, and true glassmorphism via `ClipRRect` + `BackdropFilter(ImageFilter.blur(sigmaX/Y: 24))` over a `scheme.surface.withValues(alpha: 0.55–0.65)` fill plus a subtle 1px light-alpha border for the glass edge highlight. Selected tab uses a soft `scheme.primary.withValues(alpha: 0.14)` rounded pill behind the icon (Lucide has no filled/duotone variants, so state must be shown via color + this highlight, not a different icon glyph). Nav icons were deliberately swapped for more universally "modern" Lucide picks: `house` (not `layout_dashboard`) for home, `chart_spline` (not `chart_column`) for stats, `circle_user_round` (not plain `user_round`) for profile. ~~`piggy_bank` was kept for budget as the clearest signifier.~~ Budget tab icon changed to `wallet` per explicit user request (wanted a wallet glyph, not the piggy bank). ~~The center "+" FAB is intentionally raised further above the bar's top edge than a simple half-overlap (`_fabRaise = 10` on top of the `_fabSize/2` overlap, with `_barHeight = 74`) — user found the default half-sunk placement "agak kebawah" (felt too low); keep the FAB visibly poking up, not centered on the bar's edge.~~ Overcorrected: user then found that raised FAB "agak terlalu keatas" (too high) and asked for it bigger but lower. Current tuning: `_fabSize = 64` (bigger), `_fabPokeAbove = 22` — deliberately **less than half** of `_fabSize`, so most of the button sits embedded/sunk into the bar and only a modest cap pokes above its top edge. When adjusting this again, reason in terms of `_fabPokeAbove` (pixels poking above the bar's top edge) rather than an additive "raise" on top of a symmetric half-overlap — it's the more direct knob for "how much floats above vs. sinks into the bar."
- [2026-09-22] - The floating nav bar's glass panel itself was always transparent-by-design outside the pill (`Stack`/`SizedBox`/`SafeArea` have no fill) — the "kenapa bukan transparent, malah hitam" complaint was actually caused by each shell screen's own **nested** `Scaffold` (`DashboardScreen`, `ProfileScreen`, etc.) painting its full-height opaque `scaffoldBackgroundColor` (true black) behind the bar, combined with too little `ListView` bottom padding — the list content ended well above the bar, so there was nothing there to show/blur, just flat opaque scaffold black. Fix: `FloatingNavBar.clearance` (`= _bottomGap + _barHeight + AppSpacing.md`) is now the canonical bottom-padding value every scrollable screen under `AppShell` should use on its last padding edge, so content actually extends behind the glass (visible through the blur) instead of leaving a dead gap, and so the last list item isn't hidden under the opaque pill. Apply this to any new scrollable screen added under the shell. ~~True glassmorphism via `scheme.surface.withValues(alpha: 0.55–0.65)` fill~~ — even after the `clearance` fix made content actually scroll behind the bar, the glass still read as solid opaque black and appeared to "block"/hide list items (`ProfileMenuSection` cards) scrolled behind it, because on this `darkIsTrueBlack` theme a 0.65-alpha `surfaceContainerHigh` tint over blurred near-black content is still ≈black — there's no headroom for blurred content to show through. Fixed by lowering the fill to `alpha: 0.38` (dark) / `0.55` (light) and bumping the border to `alpha: 0.2` (dark) for definition — now blurred list-item text/shapes are visibly legible through the pill instead of vanishing into it. On a true-black theme, glass fill alpha needs to stay well under ~0.5 or it stops reading as translucent at all.
- [2026-09-22] - `flutter run -d chrome` (the `flutter-web` config in `.claude/launch.json`, port 8788) cannot compile this app at all: `sqlite3_flutter_libs`/`sqlite3`'s native `dart:ffi` bindings are not web-compatible (`Only JS interop members may be 'external'` from `libsqlite3.g.dart`, then the frontend server crashes outright). This is a real architectural gap, not a bug in feature code — Drift needs a web-specific backend (e.g. `drift/wasm`) before this app can ever run in the Browser pane. Until that's wired up, do not spend time trying to visually verify UI changes via the `flutter-web` preview; rely on `flutter analyze` (must stay at 0 issues) plus reading the widget tree, and tell the user visual verification isn't currently possible in-browser.
- [2026-09-22] - Rebuilt `features/budget/presentation/budget_screen.dart` from a placeholder into the real "Anggaran" screen (budgets list, savings goals, wallet/Dompet summary) per user-supplied reference screenshots. Since no feature in this app is wired to Drift for live CRUD yet (dashboard also hardcodes placeholder `0` values, `add_transaction_screen.dart` is still a stub), the budget/savings-goal data intentionally stays as local `StateProvider<List<...>>` in `budget_providers.dart` (empty by default → real empty-state), not a Drift table — added a real `features/accounts/{domain,data,presentation}` (reading the pre-existing `Accounts` table) for the "Dompet" section instead, since that table already existed. "+" buttons on this screen show a "segera hadir" `SnackBar` (same established pattern as `features/profile`), since no add-budget/add-goal screens exist yet — build those as their own follow-up task rather than assuming this screen's `+` buttons are wired.
- [2026-09-22] - Brand accent is **blue** (`#3D7FFF` seed via a custom `FlexSchemeColor`), not the `FlexScheme.money` green. Dashboard/home defaults to `ThemeMode.dark` with `darkIsTrueBlack: true` for the near-black "fintech" look (cards use `scheme.surfaceContainerHigh`/`surfaceContainerHighest`, decorative accents use `scheme.primary.withValues(alpha: ...)` circles) — reference mock was a lime-green dark dashboard with rounded cards and a floating bottom nav (center raised "+" button); user explicitly asked for blue instead of the mock's lime when asked to clarify. Confirmed again when the Statistik/reports screen mockup also used lime — user chose to keep blue rather than match the mock, so **mockup accent colors are reference for layout only, never for hue** unless the user says otherwise.
- [2026-09-22] - `lib/features/transactions`, `lib/features/categories`, and `lib/features/accounts` have no data/domain layer at all yet (no repository, no freezed model — only the Drift tables exist). Any new feature that needs to aggregate across them (e.g. `reports`) should query `AppDatabase` directly from its own `data/<feature>_repository.dart` (join `Transactions`/`Categories`/`Accounts` there) rather than importing another feature's repository — satisfies the no-cross-feature-import rule and avoids blocking on building out those other features first. Once `transactions`/`categories`/`accounts` get real repositories, revisit whether `reports` should depend on them instead of querying tables directly.
- [2026-09-22] - Shared widgets get promoted from a feature's `presentation/widgets/` into `core/widgets/` the moment a second feature needs the same one — done for `SuggestionCard` (was dashboard-only) and `MenuSection`/`MenuSectionItem` (was `ProfileMenuSection`/`ProfileMenuItem`, profile-only) when the `reports` screen needed both. This is the four-file rule (COMPONENTS.md) in practice, not a special case.
- [2026-09-22] - Added `formatRupiahCompact(int amount)` to `core/utils/formatters.dart` for tight spaces (chart bar labels, stat tiles): `523000` → `Rp523rb`, `13500000` → `Rp13,5jt`, via `NumberFormat('#,##0.#', 'id_ID')` (comma decimal is automatic for the `id_ID` locale). Falls back to `formatRupiah` under Rp1.000. Use this instead of a bespoke abbreviation formatter anywhere a full `formatRupiah` string would overflow.
- [2026-09-22] - `flutter-web` (the only configured launch target, port 8788) cannot run this app at all — `AppDatabase` connects via `NativeDatabase.createInBackground` (`package:drift/native.dart`), which pulls in `sqlite3`'s `dart:ffi` bindings, and `dart:ffi` isn't available on the web compiler target (`Error: Dart library 'dart:ffi' is not available on this platform`). This is a pre-existing constraint, not something a UI change can trigger or fix. UI/feature verification for this project can only be done via `flutter analyze` (must stay clean) plus manual code review, or by running on an actual Android/iOS/desktop target — the browser preview tooling is not usable here until a web-safe Drift connection (e.g. `drift/wasm.dart`) is added, if ever.
- [2026-09-22] - When the reports/statistics feature needed per-day and per-month expense bars, built simple hand-rolled `Row`/`Container` bar columns (`ReportBarColumn`) with `flutter_animate`'s `.scaleY()` grow-in instead of reaching for `fl_chart`'s `BarChart`, because the mockup needed a value label *above* each bar and an axis label *below* it — `fl_chart` makes per-bar top-labels awkward. Reserved `fl_chart` (`PieChart`) for the donut/category breakdown, which is its natural fit. If a future chart needs true interactivity (tooltips, pan/zoom), reach for `fl_chart` properly instead of extending the hand-rolled bars.
- [2026-09-22] - `docs/blueprint/STRUCTURE.md` and `COMPONENTS.md` had drifted from the actual codebase (missing `features/budget` and `features/profile` entirely, and described a per-widget-folder "four-file rule" for `core/widgets/` that was never actually followed — real convention is flat files + a `widgets.dart` barrel, folder-per-widget only once a widget needs more than one file). Fixed both docs to match reality and added a "Known gaps" section to STRUCTURE.md listing empty dirs (`transactions/{data,domain}`, all of `categories/`) and doc-only files that don't exist (`app_typography.dart`, `core/constants/app_constants.dart`). When blueprint docs and code disagree, trust the code and fix the doc — don't assume the doc describes an aspirational target unless the user says so.
