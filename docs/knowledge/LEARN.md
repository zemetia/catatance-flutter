# Correction & Mistake Log

Entries are appended here whenever the user corrects the AI or the AI self-identifies a deviation from the blueprint or the user's intent. Empty at project start — this file grows over time.

[2026-09-22] - `StateProvider` from `flutter_riverpod: ^3.4.3` is not exported from the main `flutter_riverpod.dart` barrel anymore - `import 'package:flutter_riverpod/legacy.dart';` is required to use it - When adding a simple `StateProvider<T>` on Riverpod 3.x, import `package:flutter_riverpod/legacy.dart` explicitly instead of assuming the default import covers it; `flutter analyze` will flag the missing symbol immediately if forgotten.

[2026-09-22] - Two Claude Code sessions were editing this same project concurrently (both building the dashboard restyle + floating nav bar independently), which briefly caused overlapping/duplicate files (`features/budget/` vs `features/budgets/`) and a shared dev server port conflict on 8788 - Before assuming a file changed unexpectedly is corruption, check whether another active session/dev-server is running on the same project and reconcile rather than overwrite - When multiple sessions touch the same Flutter template project at once, expect duplicate scaffolding for the same feature and de-dupe by keeping whichever is already wired into the router/shell.

[2026-09-22] - Ran `taskkill /F /IM chrome.exe /T` on Windows to stop a verification `flutter run -d chrome` instance, which kills every Chrome process on the machine by name (the user's own browser windows, other sessions' Chrome instances) instead of just the one started for verification - Stop a specific dev-server browser by PID (e.g. resolve the PID via `Get-NetTCPConnection -LocalPort <port>` or the `flutter run` process itself, then `Stop-Process -Id <pid>`) or let the harness's own preview/task-stop tooling tear it down, never a blanket `taskkill /IM chrome.exe` - On Windows, any `taskkill`/`Stop-Process` by image name instead of PID is a destructive, unscoped action; always scope kills to the specific PID you started.

[2026-09-22] - Used `ref.watch(someStreamProvider).valueOrNull` when rebuilding the budget screen (`lib/features/budget/presentation/budget_screen.dart`, `lib/features/accounts/presentation/account_providers.dart`) and `flutter analyze` failed with `undefined_getter` - `riverpod: 3.4.3` (installed via `flutter_riverpod: ^3.4.3`) removed the `valueOrNull` getter from `AsyncValue`; `value` itself is now nullable (`ValueT? get value`), so use `.value ?? fallback` instead - On this project's Riverpod 3.x, always read an `AsyncValue`'s data with the nullable `.value` getter, not `.valueOrNull` (that API is from Riverpod 2.x docs/muscle memory and no longer exists here).

[2026-09-22] - Project had package name / applicationId configured as `com.zymermusic.pencatatan_keuangan` instead of `com.zemetia.pencatatan_keuangan` - Renamed Kotlin directory structure from `com/zymermusic/` to `com/zemetia/`, updated `namespace` and `applicationId` in `android/app/build.gradle.kts`, `MainActivity.kt`, and all platform configurations (iOS, macOS, Linux, Windows) - All bundle identifiers and application IDs in this repository belong to the `com.zemetia` organization.

[2026-09-22] - Guessed Lucide icon names by analogy to other icon sets (`LucideIcons.check_circle_2`, `.bar_chart_3`, `.fingerprint`) when building the new Profile settings screens, and `flutter analyze` failed with `undefined_getter` for all three - The actual `flutter_lucide` names are `circle_check_big`, `chart_bar`, and `fingerprint_pattern` (verified by grepping `static const IconData` in the installed package at `<pub-cache>/hosted/pub.dev/flutter_lucide-<version>/lib/src/flutter_lucide.dart`) - Don't guess `flutter_lucide` icon names from memory of other icon libraries (Material Icons, FontAwesome); grep the installed package source for the exact identifier before using an icon you haven't already seen used elsewhere in this codebase.
[2026-09-22] - Drift schema changes (such as adding `currencyCode` or `Debts` table) must immediately trigger `dart run build_runner build` to update `app_database.g.dart`; otherwise, companion classes and generated table columns will fail compilation with undefined parameters - Run `dart run build_runner build` after modifying any Drift table definitions or Freezed models - Always ensure generated code is updated before running analyzer or tests.
[2026-09-22] - Android Gradle build on Windows failed with `:local_auth_android:compileDebugKotlin` due to `this and base files have different roots: C:\... and D:\...` in Kotlin incremental compilation cache - Added `kotlin.incremental=false` in `android/gradle.properties` - When a Flutter project is on a different drive letter (D:) from the global Pub cache (C:), Kotlin incremental compilation fails to resolve relative paths across drive roots; set `kotlin.incremental=false` to ensure reliable Android builds.

[2026-09-23] - `lib/features/bank_notifications/domain/known_bank_apps.dart`'s preset package names (BCA mobile, BNI Mobile Banking, Livin' by Mandiri, Jenius, digibank by DBS, OCTO by CIMB Niaga, DANA, ShopeePay, LinkAja) were all guessed by naming-convention analogy (e.g. `com.bca.mobile`, `com.bni.mobilebanking`) instead of looked up, so none of them matched the real app's actual Android package — meaning the bank-notification listener could never have matched a genuine notification from those apps, a much larger bug than a stale status card. - Verified every entry's real package name via web search against its live Google Play Store listing before writing it into the preset list (e.g. real BCA mobile is `com.bca`, real Livin' by Mandiri is `id.bmri.livin`, real Jenius is `com.btpn.dc`). - Never guess a third-party app's Android package name from its display name/branding pattern, even when the guess "looks right" — always verify against the actual store listing, same lesson as not guessing `flutter_lucide` icon identifiers.

[2026-09-23] - The "Tangkap Notifikasi Bank" settings screen kept showing "Akses notifikasi belum aktif" even after the user enabled notification access in the system's notification-listener settings screen and returned to the app - `notificationListenerStatusProvider` (`FutureProvider.autoDispose<bool>` in `bank_notification_providers.dart`) was never re-fetched after the user came back from that system settings screen (a separate Activity, not a Flutter route pop) — `BankNotificationSyncObserver`'s `didChangeAppLifecycleState(resumed)` handler only synced the pending-notification queue, not this status. Fixed by also calling `ref.invalidate(notificationListenerStatusProvider)` there. - Any `FutureProvider` reading OS-level permission/settings state that the user grants by leaving the app (not by popping a route) must be explicitly invalidated on `AppLifecycleState.resumed`, not just left to Riverpod's normal caching — the widget lifecycle alone won't trigger a re-fetch since the screen never actually rebuilds from scratch.

[2026-09-23] - Expanded the default category list in `seedInitialData()` (`lib/core/database/seed_data.dart`) but the user's already-installed app still showed the old, narrower category list in Transactions/Budget/everywhere - `seedInitialData()` only runs from `onCreate` (fresh DB) and from `beforeOpen` when the `accounts` table is empty, so an existing install with data never re-seeds; editing the seed function alone only affects brand-new installs - Any change to default/seeded rows (categories, etc.) needs a matching `schemaVersion` bump + `onUpgrade` migration step (`from < N`) that applies the same change to already-installed databases (rename existing rows in place to keep `categoryId` references valid, insert new ones) — the seed function and the upgrade path must be updated together, same pattern already used for "Cicilan & Pinjaman" (v7), "Biaya Admin Transfer" (v10), and "Transfer Keluar/Masuk" (v11).

When asked to use `git checkout --` to resolve the conflict (safe, since the patch was already saved), the user explicitly declined ("jangan di stash dan jangan git checkout") and asked for the pop-retry path instead - Don't test with `git stash` on a project another session may be actively editing; if a `git stash pop` conflicts, ask before touching git state further rather than assuming the safer-looking option (`git checkout --` a conflicting file) is welcome — the user may have a strong preference for a different resolution even when both are equally safe.
